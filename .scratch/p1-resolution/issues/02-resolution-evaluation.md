# Resolution evaluation: ordered applicable set, winner, first-provider-wins values

Type: task
Status: resolved
Blocked by: 01

## Question

Per ADR-0015, extend evaluation so a query can resolve candidates instead of only matching. The fixed pipeline (bbox → property → exact DE-9IM) is unchanged; resolution is a layer over the collected applicable rules.

- **Applicable** = the query's spatial predicate holds + where-clause admitted (`reaches_relate`) + not excluded — the same set `rule_ids` reports today.
- **Order** the applicable set by precedence: priority desc, then declaration order (ascending rule id).
- **Winner** = head of the ordered set.
- **Values** = first-provider-wins merge of rule `properties` down the order: each field takes its value from the highest-precedence applicable rule defining it; a field defined by no applicable rule is absent.
- **Collect-then-resolve**: no early-exit — the merge needs the full set (ADR-0015 stance).
- Add a resolve path alongside `evaluate`/`evaluate_mask` producing the per-candidate resolved outcome (`core/src/evaluate.rs`).

Tests: overlapping rules with known priorities → winner and merged values; gap-fill (a field comes from a lower-precedence rule when the winner lacks it); tie → declaration order; where-clause admission; `excludeRuleIds`.

Run: `cargo test --workspace` and `cargo clippy --workspace --all-targets` — green before commit.

## Agent Brief

**Category:** enhancement
**Summary:** Evaluate candidates to an ordered applicable set, a winner, and first-provider-wins derived values.

**Current behavior:**
A query reports per candidate which rules matched (rule ids in deterministic ascending order). There is no precedence, no winner, and no value extraction.

**Desired behavior:**
- A resolve path (parallel to the existing match path) computes, per candidate:
  - the **applicable set** — rules where the query's spatial predicate holds, the `where` clause admits them, and they are not excluded;
  - the **order** — priority descending, ties by declaration order (ascending rule id);
  - the **winner** — head of the ordered set;
  - the **values** — first-provider-wins merge of the applicable rules' properties down the order: each field takes its value from the highest-precedence applicable rule that defines it; a field defined by no applicable rule is absent.
- **Collect-then-resolve**: all applicable rules are gathered before resolving; no early-exit on the first spatial hit (ADR-0015 stance).
- The existing match path and its mask output are unchanged.

**Key interfaces:**
- The ruleset/engine query surface — a resolve variant returning the per-candidate resolved outcome (winner, values, applicable)
- Per-rule priority access from ticket 01
- Reuses the existing bbox → property → exact DE-9IM pipeline and its admission logic

**Acceptance criteria:**
- [ ] Two overlapping rules with priorities 10 and 5 → winner is the priority-10 rule; values merge fields from both when the winner lacks a field the lower rule defines
- [ ] Equal priorities resolve deterministically by declaration order
- [ ] A rule failing the `where` clause, or excluded via `excludeRuleIds`, is not in the applicable set and contributes no values
- [ ] A candidate matched by no rules yields the not-resolved outcome
- [ ] The existing match path and mask output are unchanged
- [ ] `cargo test --workspace` and `cargo clippy --workspace --all-targets` are green

**Out of scope:**
- The napi/wrapper API (ticket 04)
- Field subset selection
- The early-exit optimization

## Answer

Implemented in commit `e9eeb31` (feat(core): resolution — rule priority, ordered applicable set, ...).

- `PreparedQuery::evaluate_resolve` (+ `evaluate_resolve_all`) gathers the **applicable** rules through the shared `relate_touched` loop (spatial predicate holds + where admits + not excluded), orders them by precedence (priority desc, ties by ascending rule id), and returns `ResolutionOutcome::Resolved { winner, values, applicable }` — the winner is the head, `values` a first-provider-wins merge down the order.
- **Collect-then-resolve**: no early exit; the merge needs the full set (ADR-0015 stance).
- `Ruleset::resolve` is the batch seam; `Ruleset::resolve_mask` / `PreparedQuery::evaluate_resolve_mask` add the compact `0/1/2` mask without materialising winner/values/explanation.
- The existing match path (`evaluate`/`evaluate_mask`/`query`/`query_mask`) is unchanged.
