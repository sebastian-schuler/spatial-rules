# Top-level priority field: schema, ingestion, canonical round-trip, validation

Type: task
Status: resolved

## Question

Per ADR-0015, rules carry precedence as a top-level integer `priority` field on the rule Feature (a GeoJSON foreign member beside `id`/`properties`/`geometry`). Implement the data-model half:

- `core/src/rule.rs`: add a `priority: i64` field to `Rule`, with serde `#[serde(default)]` so pre-P1 canonical strings load as `0`.
- `core/src/ingestion.rs` (`rule_from_feature`): read the top-level `priority` from the feature. Missing → `0`; present-but-not-an-integer (string/float/bool) → `SR_RULESET_CONSTRUCTION_FAILED` naming the rule. A `priority` inside `properties` stays plain metadata and is never read by resolution.
- `core/src/ruleset.rs` (`build_with`): hoist priorities into a typed `Vec<i64>` aligned to `RuleId` for fast resolution access.
- Canonical form (ADR-0013) round-trips the field automatically via `Rule` serde; confirm old canonical fixtures (no `priority`) still load as `0`.

Tests: ingestion (missing / wrong-typed / integer), canonical round-trip, old-canonical compatibility, wrong-type build failure.

Run: `cargo test --workspace` and `cargo clippy --workspace --all-targets` — green before commit.

## Agent Brief

**Category:** enhancement
**Summary:** Add a top-level integer `priority` field to rules that resolution reads for precedence.

**Current behavior:**
Rules are `{id, properties, geometry}` with no engine concept of precedence. A `priority` property inside `properties` (as in the plan's rule examples) is treated as plain metadata.

**Desired behavior:**
- Every rule may carry a top-level integer `priority` field in its GeoJSON feature (a foreign member beside `id`/`properties`/`geometry`) and in the ADR-0013 canonical rule record.
- Missing `priority` → `0`. Present-but-not-an-integer (string, float, bool) → ruleset construction fails with `SR_RULESET_CONSTRUCTION_FAILED`, naming the rule.
- Pre-P1 canonical strings (no `priority`) load with priority `0`.
- A `priority` inside `properties` remains plain metadata and is never read for precedence.
- Priorities are available to the query path in priority-descending-then-declaration order without re-parsing properties per candidate.

**Key interfaces:**
- `Rule` — gains `priority: i64`, defaulted so canonical round-trip and old-canonical load both work
- Rule ingestion — reads the top-level `priority`; missing → `0`, wrong type → construction error
- `Ruleset` — exposes per-rule priority to the resolution path (priority desc, tie-break ascending rule id)

**Acceptance criteria:**
- [ ] A rule with top-level `priority: 10` ingests and reports priority 10
- [ ] A rule without `priority` reports 0
- [ ] A rule with `priority: "high"`, `2.5`, or `true` fails construction with `SR_RULESET_CONSTRUCTION_FAILED` and names the rule
- [ ] `toCanonical()`/`fromCanonical()` round-trip `priority`; a canonical string without `priority` loads as 0
- [ ] A `priority` inside `properties` is not read by the priority machinery
- [ ] `cargo test --workspace` and `cargo clippy --workspace --all-targets` are green

**Out of scope:**
- The resolution evaluation itself (ticket 02)
- A configurable priority key
- Any change to how `where` filters work

## Answer

Implemented in commit `e9eeb31` (feat(core): resolution — rule priority, ordered applicable set, ...).

- `Rule` gains `priority: i64` (`#[serde(default)]` → 0), so pre-P1 canonical strings load as 0 and the canonical round-trip carries the field.
- `rule_from_feature` reads the top-level `priority` foreign member; missing → 0; wrong-typed or negative → `SR_RULESET_CONSTRUCTION_FAILED` naming the rule. The canonical load gate (`Ruleset::from_canonical`) applies the same validation via the shared `validate_priority`.
- `Ruleset` hoists priorities into a `Vec<i64>` aligned to `RuleId` and exposes `priority(rule_id)`.
- `properties.priority` stays plain metadata and is never read for precedence.

Amended 2026-08-23 (loose-end resolution): negative priorities are now rejected at both ingestion gates. A negative integer would silently sort below unprioritized (0) rules, breaking ADR-0015's "unprioritized rules sort below any explicit priority" invariant — the same class of silent precedence misreading the wrong-type gate exists to prevent. ADR-0015 was amended to say priorities are non-negative integers.
