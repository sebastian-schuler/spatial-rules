# Resolution model: top-level priority, ordered applicable set, first-provider-wins values, flat explanation

The engine evolves from matcher to policy engine (roadmap P1): per candidate, instead of "these rules matched", resolution answers "what is the effective rule, what values apply, and why". Resolution is built from one primitive — the **ordered applicable set**: the rules admitted for a candidate (the query's spatial predicate holds, the `where` clause admits them, exclusions applied), ordered by precedence. The **winner** is the head of that order; **derived values** are a first-provider-wins merge of rule properties down the order (each field takes its value from the highest-precedence applicable rule that defines it; a field no applicable rule defines is absent); the ordered set **is** the explanation, each member carrying `{ruleId, priority, spatialMatched, propertyMatched}` — data the evaluation already computes, so explanation is free. This settles the roadmap gate: "No P1 implementation starts before the precedence/conflict-resolution model is decided."

Precedence: a rule's precedence is a **top-level integer `priority` field** on the rule Feature (a GeoJSON foreign member beside `id`/`properties`/`geometry`; additive to the ADR-0013 canonical rule record with `#[serde(default)]`, so pre-P1 canonical strings load as priority 0). A `priority` property inside `properties` is plain metadata and never read by resolution. Higher wins; a missing field is 0 (unprioritized rules sort below any explicit priority); equal priorities break by **ruleset declaration order** — the existing deterministic ascending rule-id order, rule ids being assigned at build in FeatureCollection order. A present-but-wrong-typed `priority` (string/float/bool), or a negative integer, is a `SR_RULESET_CONSTRUCTION_FAILED` build error naming the rule, because silent misreading of precedence is exactly the bug the top-level field exists to prevent — a negative priority would silently sort below unprioritized (0) rules, breaking the "unprioritized rules sort below any explicit priority" invariant. Priorities hoist to a typed `Vec<i64>` aligned to `RuleId` at compile; no index is built (applicable sets are small; ordering is O(m log m) per candidate).

Performance: resolution is **collect-then-resolve** — the first-provider-wins merge needs the full applicable set, so the engine cannot early-exit at the first spatial hit. A priority-ordered evaluation with early exit is a documented later optimization. At the ~1k×30 production scale applicable sets are small, and the mask hot path is unchanged.

API: resolution is a new surface, not a query flag. `resolve(candidates, query)` (and `resolveAsync`, mirroring ADR-0009) returns a chainable `ResolutionResult` following ADR-0014's contract: `mask()`/`count()`/`summary()` derive from the native compact mask (`0` no resolution, `1` resolved, `2` invalid) with zero rich cost; `toJson()` is the one lazy native rich call returning per-candidate `{outcome, winner, values, applicable}`. `query()` and its mask stay untouched, and the query shape is shared (`spatial`/`where`/`excludeRuleIds`). Field subset selection (`resolveFields`), a first-class `action: allow|deny` type, and a geometric-specificity dimension are deferred as additive (specificity in particular is expressible later as data on top of priority).

Verification: turf.js cannot oracle resolution, so the suite uses property tests over synthetic overlapping rule sets — asserting winner/values determinism and priority-order invariants across repeat evaluations and across both spatial-index kinds — plus hand-checked precedence cases.

## Considered Options

- **Reserved `priority` property name** — rejected: collides with legitimate metadata use; an application's `priority` property that means something else would silently become a precedence declaration.
- **Configurable priority key (`priorityKey`) at ruleset build** — rejected: metadata-safe only when configured; a defaulted `priority` still collides and the key must be remembered per ruleset.
- **Single-winner-only resolution** — rejected: it drops the lookup-table semantics, and the spatial lookup table is a stated P1 destination.
- **Field-wise merge only, no winner** — rejected: the "which rule wins?" policy question is also a P1 destination; the winner falls out of the same order for free.
- **Priority + geometric specificity as a built-in dimension** — rejected: "which geometry is more specific" is ambiguous and costs area computation; a composable chain (priority → specificity → first-match) is the documented extension path, not the v1 mechanism.
