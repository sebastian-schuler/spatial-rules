# Query/replacement API: sync-first with a benchmark trigger

v1 ships synchronous `query()` and `replace()` — simplest and correct for the workload; the request path never touches a partial build (`docs/Initial-plan.md` §37). An asynchronous `queryAsync()` (off the JS thread via `#[napi] async fn`, ADR-0006) is added only if the benchmark harness shows the sync query's p95 latency exceeding 50 ms on the ~1,000-candidate production workload (§28). `replace()` returns the ADR-0007 observability (`lastSwapTime`, `buildDurationMs`, active ruleset id/count).

Amended 2026-08-19 (ADR-0012/post-v1 ticket 06): the latency gate did **not** trigger — the load harness (`bun run bench load`, `benchmarks/js/server-bench.mjs`, `docs/benchmarks.md` §3b) measured a single-process CPU ceiling of ~165 rps raw / ~130 rps JSON on 1,000×30, with p95 ≈ 32 ms over HTTP — but the sync napi call fully consumes the event loop under load (`/health` latency ≈ query latency). `queryAsync()` is therefore added as an **opt-in** lever on the throughput / event-loop-headroom axis, not the latency axis this ADR originally judged. It is byte-for-byte identical to `query()` (same mask, same `SR_*` error model as a Promise rejection), runs the parse + query off the JS thread (see the 2026-09-17 correction below on *which* runtime), copies the candidate buffer once per call, and leaves `query()` as the default. Sync `query()` is unchanged.

Amended 2026-08-21 (shape unification): `queryAsync()` now returns `Promise<QueryResult>` — the same chainable result as `query()` (terminals per ADR-0014) — rather than a raw `Uint8Array`, and accepts the same broadened inputs (`GeoJsonInput`/`QueryInput`) normalized identically to `query()`. The mask, the `SR_*` Promise-rejection error model, the single buffer copy, and off-main-thread execution are unchanged.

Corrected 2026-09-17 (HTTP-serving research, `.scratch/perf-memory/research/01-http-serving-optimizations.md`): `queryAsync` does **not** run on libuv's threadpool, so the 2026-08-19 wording above (and the "contends with fs/DNS/crypto/zlib" framing) is wrong for this dependency set. napi-rs 3.x — `node/Cargo.toml` enables `napi = { version = "3", features = ["napi8", "async"] }`, pinned 3.12.1 — runs `#[napi] async fn` on a **NAPI-RS-managed Tokio runtime**; `AsyncTask<T>` is the abstraction that uses the libuv pool (napi-rs "Async and concurrency" decision table, https://napi.rs/docs/more/async-concurrency). Two consequences: (1) `UV_THREADPOOL_SIZE` is not the knob for `queryAsync`; napi-rs documents that "a long synchronous calculation inside [an `async fn`] still occupies a Tokio worker thread" and recommends `spawn_blocking` or `AsyncTask` for blocking work — `queryAsync` is exactly such a CPU-bound call, so the levers are `AsyncTask` (libuv) or a custom runtime (`create_custom_tokio_runtime` with an explicit `worker_threads` count); (2) the default Tokio worker count is not stated in the docs, so how many `queryAsync` calls actually run concurrently is **unmeasured**. The shipped behaviour, the single copy, and the byte-identical mask are unchanged.
