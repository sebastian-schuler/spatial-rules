# Distance predicates: spherical great-circle (Haversine) meters, minimum-distance admission, bounding-circle pre-filter

Distance is a new **metric** predicate surface, not DE-9IM (ADR-0012 already scoped "distance" out of the overlap predicate). The roadmap gate — "CRS/geodesic semantics must be decided and documented before distance lands" — is settled here: distance is measured with the **spherical great-circle (Haversine)** model, in **meters**, on WGS84 lon/lat, consistent with the engine's existing spherical geodesic-area stance (overlap metrics use `GeodesicArea`; Initial-plan §14: "WGS84 longitude/latitude coordinates MUST NOT simply be treated as planar"). Longitude is **not normalized at ingestion** — the engine treats it as an ordinary coordinate, consistent with the DE-9IM predicates (edge-matrix tests) — and Haversine is antimeridian-safe by construction (its Δλ term is invariant to ±360 wrap), so within the GeoJSON-conformant convention (coordinates in [−180, 180] / [−90, 90]) distance results are never ambiguous at ±180; the ~0.3–0.5% spherical error is acceptable for the geofencing/parking/delivery use cases. (Out-of-range longitude is outside that convention: the withinDistance pre-filter may miss such a rule across ±180 even though the exact check would be correct.) The ellipsoidal **Karney geodesic** is the documented higher-accuracy additive alternative; planar Euclidean and rhumb are rejected.

The predicate is **`withinDistance`**: "the candidate is within N meters of the rule". The distance is the **minimum** candidate↔rule distance — 0 when the candidate is inside the rule (geo's `HaversineClosestPoint` returns the closest point on the rule, `Intersection` when contained) — and symmetric, so there is no candidate→rule directionality. **v1 supports point and multipoint candidates** (the geofencing positioning case — a GPS fix within N of a zone); a Polygon/MultiPolygon candidate with `withinDistance` is reported as an invalid outcome (`withinDistance requires a point candidate`), because geo exposes no spherical polygon↔polygon minimum distance and the ADR's mechanism is point→geometry. It enters the query as `{ "spatial": { "predicate": "withinDistance", "distance": <meters> } }`; `Query` gains `distance_meters: Option<f64>` with strict validation (`distance` required and a finite positive number for `withinDistance`; present with any other predicate → `SR_INVALID_QUERY`). Evaluation is a **conservative bounding-circle pre-filter** — expand the candidate's envelope by N meters using latitude-dependent degrees-per-meter, query the R-tree, whose entries are the rules' **great-circle (arc-aware) envelopes** rather than their planar bounding boxes (a planar box falls short of its edges' arcs at high latitude and would let the pre-filter drop a genuinely-within rule — see the amendment below), plus the wrapped longitude complement when the expansion crosses ±180, then confirm exactly with `HaversineClosestPoint` + `Haversine.distance` — never dropping a within-N rule. `withinDistance` admits rules into the resolution applicable set exactly as the DE-9IM predicates do (ADR-0015), so resolution, derived values, and explanation work unchanged over distance admissions. `nearest` is a documented Non-Goal (Initial-plan §72); proximity bands compose as repeated `withinDistance`.

Amended 2026-09-17 (perf-memory tickets 09 + 11): `withinDistance` is a **spherical** predicate (its confirm, `HaversineClosestPoint`, walks edges as great-circle arcs) while the DE-9IM predicates are **planar** (`geo::relate`). v1 indexed every rule by its planar `bounding_rect` and reused it for both; a great-circle arc bulges outside that box at high latitude (and for long diagonal edges anywhere), so the distance pre-filter could drop a rule that is genuinely within N metres, violating the "never dropping" guarantee above. Found by `core/tests/proptest.rs::within_distance_never_drops_a_within_rule`.

There are now **two indexes**. The planar index is unchanged and still serves every DE-9IM predicate, for which it is exact. A second **fringe** index — one great-circle box per rule, from `core/src/model/spherical_envelope.rs` (0.1° arc sampling, ~11 m margin), holding only rules whose arcs escape their planar box — is consulted *only* by the distance pre-filter, which unions the two hit sets. It is built **lazily** on the first distance query, so a ruleset that never runs one pays nothing for it (the same lazy stance as the prepared-geometry memo, ADR-0010).

An **edge-granular** fringe (one box per escaping edge) had better selectivity but grows with *vertices*, not rules: at 100k rules it measured **816 → 1626 B/rule** (77.8 → 155.1 MiB) — rejected. One box per rule is bounded by rule count, and the lazy build makes its cost zero for rulesets that never query distance.

Costs (30 rules × 1,000 points, ticket-11 A/B via `bun run bench samples`):

| | planar-only (buggy) | arc-hull, eager, shared index | split + lazy fringe (shipped) |
|---|---|---|---|
| `within_distance_mask` | 131.9 ms | 336.9 ms | **~392 ms** |
| point `mask_baseline` (DE-9IM) | 1.50 ms | 2.74 ms | **1.55 ms** |
| 100k×10 `bytes/rule` (memory grid) | 816 B | 816 B | **818 B** |

So correctness and the DE-9IM paths are recovered completely; the residual is pre-filter selectivity on the distance surface, which is the price of a box filter over arc geometry. The public `Ruleset::envelope` accessor stays planar. A further selectivity step (a small, bounded set of per-edge boxes, e.g. K-way clustered) remains open if distance throughput demands it.

## Considered Options

- **Planar (Euclidean) meters** — rejected: geo's own docs call Euclidean distance on lon/lat "nonsense"; violates Initial-plan §14's "never treat lon/lat as planar".
- **Ellipsoidal Karney geodesic** — deferred as additive: nanometer-accurate and antipodal-correct, but a heavier, different model than the spherical area path already uses; not needed for the v1 geofencing semantics.
- **Rhumb (loxodrome) distance** — rejected: constant-bearing distances are a routing concern, not an admission predicate.
- **Centroid/representative-point distance** — rejected: a point deep inside a large zone must read as distance 0, not a large centroid distance.
- **`SpatialPredicate::WithinDistance(f64)` payload variant** — rejected: breaks the payload-free Copy enum used across the match/resolve paths; the query-level `distance_meters` keeps the enum unchanged.
- **Sibling top-level distance flag** — rejected: a predicate-specific shape belongs inside `spatial`, validated at parse.
