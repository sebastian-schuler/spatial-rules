# Chainable query result API

The public query surface decouples the evaluation from its output format: `query()` returns a chainable `QueryResult` instead of a bare mask, so one native evaluation serves every view. `toMask()` returns the primitive `Uint8Array` mask (0/1/2, aligned to input, 1 byte per candidate); `toIndices()`/`invalidIndices()` return exactly-sized `Uint32Array`s of matched/invalid positions; `count()` and `summary()` ({matched, notMatched, invalid}) are cheap derivations; `toGeoJson()` returns the matched features as a FeatureCollection string with properties preserved from the original payload (no lossy round-trip through the engine's parsed candidates); `toRichJson()` returns per-candidate outcomes + overlap as a JSON string, **lazily** — one native call on first use, then cached (ADR-0012). The design keeps the JS↔Rust boundary byte-oriented and minimal (ADR-0006): `query()` is the only native crossing for the cheap views, all derived in the wrapper from the captured mask + original buffer; the rich view is the exception because rule ids/overlap can only be computed natively, so it is deferred until asked so mask-only callers pay nothing. Benchmarks consume the raw binding, so the hot-path mask measurement is unchanged.

Alternatives considered: one method per format (`query`/`queryRich` + prospective `filteredGeojson`/`keepIndices` — proliferation, and N formats = N re-evaluations); a `format`/`options` parameter (smallest surface, additive with a mask default, but the return type becomes parameter-dependent and two formats from one batch costs a second crossing); a native filtered-geojson method (would beat the JS re-parse at very large scales — deferred; the JS view is the chosen tradeoff at the ~1k production scale). Chainable won because the multi-format case is "compute once, format many" — one crossing serves all cheap views — and each terminal has a fixed return type.

Semantics to keep in mind: `toGeoJson` keeps matched candidates only (mask == 1), dropping unmatched and invalid; it is value-faithful (not byte-faithful) when the input was an object/string rather than a Buffer. `toRichJson` evaluates against the ruleset current at first call, so a `replace()` between `query()` and `toRichJson()` can tear mask vs rich — the mask is the snapshot and wins. Memory contract: `QueryResult` holds the candidates buffer by reference (no copy); heavy views are one-shot and never cached, so results stay lean for giant lists; results are short-lived (one request → GC). Streams are out of scope: the engine is whole-buffer/batch by design, so a stream input would only mean collect-then-query (async + fully buffered, no streaming benefit).
