# Property where operators: $not, $nin, $exists

The Mongo-style `where` subset (ADR-0003) is extended with three operators: field-level `$not` (wraps exactly one inner field-op, `{ field: { $not: { $op: v } } }`), `$nin` (`{ field: { $nin: [...] } }`), and `$exists` (`{ field: { $exists: true|false } }`). Semantics follow the engine's established rule that a missing property or type mismatch is a non-match (ADR-0003), not Mongo's: `$nin` therefore does not match a missing field, and `$not` is the logical negation of the inner predicate under that same rule — both divergences from Mongo are documented. `PropertyValue` stays scalar-typed (no arrays/objects), so `$size` is not added, and `$regex` is deferred (a regex dependency on the query hot path with no demonstrated need). No index extension: the new operators are answered by per-rule evaluation — rulesets are ~30 rules — while the `EqualityIndex` continues to answer only equality/`$in` (ADR-0003). SQL-like query language remains out of scope (Initial-plan §11); the `where` AST stays the single engine-facing representation so a string front-end could be added later without engine changes. Whole-clause `$nor` (filtering-scale ticket 02) extends the same basis: `$nor: [<where>...]` matches when zero inner clauses match, is composable under `$and`/`$or`, and is answered by per-rule evaluation (no index extension). Under the engine's missing-property = non-match rule, a `$nor` whose inner clauses reference a missing field matches — a further documented divergence from Mongo, where `$ne`-on-missing matches and would flip the `$nor` to non-match.
