# Prepared-geometry caching: thread-local owned prepared geometries

The query pipeline caches each rule's `PreparedGeometry` per thread, keyed by ruleset identity, instead of rebuilding it on every `Ruleset::prepare` call — the ladder shows preparation is the dominant ~23× lever (E/F benches), and the per-call cost was ~5 ms for 30 rules. `PreparedGeometry` is `!Send + !Sync` in geo 0.33 because its `GeometryGraph` holds an `Rc` (not because it borrows), so the cache stores the **owned** form `PreparedGeometry<Geometry<f64>>` (via `PreparedGeometry::from(rule.geometry.clone())`) in a `thread_local!`: owned prepared geometries carry no borrow of the ruleset, and `thread_local!` accepts `!Send` types, so no self-referential storage or `Send + Sync` narrowing is needed. The price is one owned prepared form per thread per ruleset; each thread pins at most one ruleset's clone, so memory stays bounded and a replacement drops the stale clone on the next query. The prepared form is **thread-affine by design**: the `Rc → Arc` change upstream makes `PreparedGeometry` `Send`, but it remains deliberately `!Sync` (its `GeometryGraph` keeps `RefCell` state), so it cannot live in the shared `Arc<Ruleset>` — which must be `Sync` for concurrent queries (`Engine` holds `RwLock<Arc<Ruleset>>`). The thread-local memo is therefore the design, not a placeholder for a future geo release.

Amended 2026-08-23 (memory-benchmark ticket 02): the cache became a **per-rule memo, filled lazily on first touch**, instead of one dense eager `Vec<PreparedGeometry>`. The `thread_local!` slot holds a `Vec<Option<PreparedGeometry>>` (interior `RefCell` so later batches can fill slots while earlier handles live), still keyed by ruleset identity and invalidated wholesale on `replace`. Two entry points split: the **hot path** (`Ruleset::prepare`/`query`/`query_mask`) exposes the memo as a `PreparedMemo` seam (keying + rule slice + shared slots bundled — the query path never sees a bare `&[Rule]`); per candidate it filters the envelope results to the rules it will relate against, prepares exactly the missing ones, then relates in envelope order — so serving memory is proportional to the rules candidates actually relate against, not the whole ruleset, and the first request no longer pays a full ruleset-sized prepare spike. A batch-level pre-pass that prepared the touched union up front was benchmarked and rejected — it runs the envelope filter twice per candidate, regressing the sparse-touch `queries_per_sec` cell by ~30% — so the per-rule check inside the loop (the ticket's sanctioned fallback) is the design. The **eager seam** (`Ruleset::prepared()`, `PreparedRuleGeometries`) keeps its dense contract — `len() == rule count`, `get(id)` valid for any id, `iter()` in ruleset order — by force-preparing every slot and snapshotting a dense `Vec` (`PreparedGeometry` is `Clone` in geo 0.33, so the snapshot clone-outs of the memo); only the benchmark ladder and API-surface tests use it. Worst case (a workload touching every rule) is unchanged at the old ceiling. Re-recorded in `docs/benchmarks.md` §Memory: serving at 100k×100 with 1,000 candidates fell ~1.8 GiB → ~286 MiB; warm throughput unchanged within run variance.
