# Prepared-geometry caching: thread-local owned geometries on geo 0.33

The query pipeline caches each rule's `PreparedGeometry` per thread, keyed by ruleset identity, instead of rebuilding it on every `Ruleset::prepare` call — the ladder shows preparation is the dominant ~23× lever (E/F benches), and the per-call cost was ~5 ms for 30 rules. `PreparedGeometry` is `!Send + !Sync` in geo 0.33 because its `GeometryGraph` holds an `Rc` (not because it borrows), so the cache stores the **owned** form `PreparedGeometry<Geometry<f64>>` (via `PreparedGeometry::from(rule.geometry.clone())`) in a `thread_local!`: owned prepared geometries carry no borrow of the ruleset, and `thread_local!` accepts `!Send` types, so no self-referential storage or `Send + Sync` narrowing is needed. The price is one geometry clone per thread per ruleset; each thread pins at most one ruleset's clone, so memory stays bounded and a replacement drops the stale clone on the next query. When geo ≥ 0.34 ships the `Rc → Arc` (`Send`) fix, the clone disappears by storing prepared geometries in the shared `Arc<Ruleset>` itself (the geo 0.33 → 0.34 upgrade is its own change to evaluate for breaking API surface).

As of 2026-08-18 geo 0.34 is not yet published on crates.io (latest: 0.33.1); the `Rc → Arc` upgrade is queued as an opportunistic change (`.scratch/post-v1/issues/05-geo-034-upgrade.md`) and lands when 0.34 ships.

Amended 2026-08-23 (memory-benchmark ticket 02): the cache became a **per-rule memo, filled lazily on first touch**, instead of one dense eager `Vec<PreparedGeometry>`. The `thread_local!` slot holds a `Vec<Option<PreparedGeometry>>` (interior `RefCell` so later batches can fill slots while earlier handles live), still keyed by ruleset identity and invalidated wholesale on `replace`. Two entry points split: the **hot path** (`Ruleset::prepare`/`query`/`query_mask`) calls `ensure_prepared`, which prepares exactly the rules a candidate touches on first touch, memoized across batches until the ruleset changes — serving memory is proportional to the rules candidates actually relate against, not the whole ruleset, and the first request no longer pays a full ruleset-sized prepare spike; the relate loop checks a predicted `None` slot per touched rule and defers the few unprepared ones (a batch-level pre-pass that prepared the touched union up front was benchmarked and rejected — it runs the envelope filter twice per candidate, regressing the sparse-touch `queries_per_sec` cell by ~30%). The **eager seam** (`Ruleset::prepared()`, `PreparedRuleGeometries`) keeps its dense contract — `len() == rule count`, `get(id)` valid for any id, `iter()` in ruleset order — by force-preparing every slot and snapshotting a dense `Vec` (`PreparedGeometry` is `Clone` in geo 0.33, so the snapshot clone-outs of the memo); only the benchmark ladder and API-surface tests use it. The `Rc → Arc` duplication fix (post-v1 ticket 05) is orthogonal — it removes per-thread duplication, this amendment removes per-rule over-preparation. Worst case (a workload touching every rule) is unchanged at the old ceiling. Re-recorded in `docs/benchmarks.md` §Memory: serving at 100k×100 with 1,000 candidates fell ~1.8 GiB → ~286 MiB; warm throughput unchanged within run variance.
